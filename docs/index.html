Constitutions your agents
can build and maintain.

A software constitution is your codebase's law — rules with evidence, counterexamples, and gates. This project provides the skill that builds it from code or interviews, the tooling that keeps it honest, and the query that finds root cause from symptoms.

Get started Read the spec

Why this exists

Projects accumulate rules that live in tribal knowledge and decay. software/constitution™ made them machine-checkable at CI time. This goes further: the constitution is built from evidence by an agent that interviews you or mines your code, maintained by detection that surfaces findings before they become incidents, and queried by symptom so root cause takes one search instead of a codebase read.

The three self-management lanes

Derived auto

The rule catalogue is a build artifact — regenerated from rule files on every push. Humans never hand-edit it.

Detect & Advise surface

Health checks find size-law crossings, drift, orphans. The agent advises you with evidence — never a drafted diff.

Human-Decided ratify

Rule changes, splits, structural evolution. You ask; the skill drafts with alternatives; you ratify.

Sample prompts

These prompts work in any coding agent that has the constitution skill installed. They cut across all sub-constitutions — replace the domain terms with your own.

Build a constitution

Greenfield

From an interview

Build a constitution for this project.
We're building a task management API in Rust
with a Postgres database. Interview me to
understand the scope, boundaries, and rules.

The skill scaffolds 8 packs, asks option-based questions per pack, and drafts rules with counterexamples from your answers.

Brownfield

From source code

Build a constitution for this repo.
Mine the codebase, tests, and CI workflows
to extract the rules this code already lives by.
Show me every doc-vs-code discrepancy you find.

The skill mines manifests, seams, tests, and docs — every rule gets evidence and a counterexample. Discrepancies become numbered findings.

Add knowledge

From source code

Architecture pack

Add to the architecture pack's knowledge:
how does our dependency injection container
work? Trace the resolution chain from the
entry point through each provider registration.

The agent reads the code, writes a knowledge fragment in STE descriptive style, and adds it to the pack with evidence citations.

From docs

Product pack

Our README describes three user personas
but the product pack doesn't cover them.
Add this to the product knowledge with
citations from the README.

The agent verifies each doc claim against code, absorbs what's confirmed, and records discrepancies as findings.

From discovery

Platform pack

I just learned our app deploys to three
environments: staging, production, and DR.
Add this to the platform pack with the
env-var differences and database topology.

The agent drafts a platform rule (each env MUST register in the environments manifest) with a counterexample, plus knowledge describing the topology.

From incident

Runbook

We just had an incident where recall
returned empty because the vector index
was corrupted. Add a runbook for this
to the testing pack.

The agent drafts a versioned runbook with trigger, blast radius, steps, and a post-incident checklist. A new rule is proposed from the scar.

Search the constitution

By symptom

Root cause lookup

Users report recall returns empty
even though memories exist.
Search the constitution for rules
about degraded retrieval lanes.
# the agent runs:
python3 scripts/query.py . \
  "recall empty degraded lane" \
  --type rules

Returns PRD-105 (the rule) + the counterexample that matches this exact incident + evidence pointing to the code.

By concept

Knowledge lookup

How does our build pipeline work?
Show me the dev pack's knowledge
about artifact generation.
# the agent runs:
python3 scripts/query.py . \
  "build pipeline artifact generation" \
  --type knowledge

Returns the knowledge fragment with prerequisites, sized for progressive loading (~200 tokens, not the full pack).

Health check

Detect issues

Check the constitution's health.
Are any packs over the size law?
Any uncatalogued rules or orphans?
# the agent runs:
python3 scripts/health.py .

Returns findings with evidence: size-law crossings, orphan fragments, uncatalogued rules, undeclared modules — advisory, never a drafted diff.

Cross-pack

Full context

I'm changing the storage layer.
Show me every rule and knowledge
fragment that touches storage
across all packs.
# the agent runs:
python3 scripts/query.py . \
  "storage database persistence" \
  --type all

Cuts across platform (storage topology), architecture (repository patterns), dev (migration rules), security (access boundaries) — one query, all packs.

What you get

scaffold

Build a constitution

# greenfield: interview
python3 scripts/scaffold.py --repo . --mode greenfield

# brownfield: mine code+docs
python3 scripts/scaffold.py --repo . --mode brownfield --docs docs/ README.md

# monorepo module
python3 scripts/scaffold.py --repo . --mode brownfield --module payments

query

Find the root cause

# by symptom
python3 scripts/query.py . "storage isolation project"

# by concept
python3 scripts/query.py . "recall degraded lane" --type knowledge

# by rule ID
python3 scripts/query.py . "PLT-002" --type rules

health

Detect before it breaks

# size law + orphans + drift + uncatalogued
python3 scripts/health.py .

# advisory in CI, blocking on --strict
# catalogue drift = CI failure (derived gate)

derive

Registry as build artifact

# regenerate catalogue from rule files
python3 scripts/derive_catalogue.py . --write

# prove committed = derived (CI gate)
python3 scripts/derive_catalogue.py .
Grounding

This project is the reference implementation of its own spec — the skill builds constitutions, the constitution governs the skill's own repository. The engram project is the original dogfood implementation.

Honest limitations

Structural-change authorization (L3 ratification) is designed but not yet implemented — it is an honour-system contract until the verification gate ships. The upstream software/constitution™ six-rule-class conformance is NOT implied by this spec.

Grounded in: SPEC.md · skill/SKILL.md · skill/scripts/ (6 portable scripts) · the engram repository (original implementation).
